## Human Review and Modifications

After the initial AI generation, a human developer performed the following reviews and modifications:

1. **Service Lifetime Adjustment**: 
   - Originally, the `ExpenseService` used static fields for in-memory storage, which caused state sharing across all instances.
   - After review, the service was refactored to use instance fields to ensure proper encapsulation.
   - The service registration in `Program.cs` was changed from `Scoped` to `Singleton` to maintain state across HTTP requests while keeping the instance state isolated per service instance.

2. **Validation Error Handling**:
   - The initial controller validation relied on automatic model state validation, but explicit validation error testing was added to the controller tests to ensure proper 400 responses.

3. **Endpoint Adjustments**:
   - The GET endpoint for filtering by category was verified to use a query string parameter (`?category=Food`) as per requirements, not a route parameter.

4. **Error Response Format**:
   - The global exception handler was adjusted to return a consistent JSON format (`{ "error": "message" }`) for all error types, as required.

5. **Testing Improvements**:
   - Enhanced test coverage for edge cases, such as validation failures and not-found scenarios.
   - Ensured each test is isolated by creating a new service instance per test (for service tests) or per test class (for controller tests).

6. **Code Quality and Style**:
   - Applied C# naming conventions and formatting.
   - Ensured proper use of `async/await`.
   - Added XML comments where beneficial for clarity.
   - Removed any unused code or unnecessary comments.

7. **Documentation**:
   - The `README.md` was expanded to include detailed setup instructions, endpoint descriptions, and example requests/responses.
   - The `AI_NOTES.md` was created to document the AI/human collaboration process.

## AI Suggestions That Were Rejected or Modified

- **Static Service State**: The AI initially suggested using static fields for the in-memory store. This was changed to instance fields to avoid unintended state sharing and to better align with instance-based service design, even though the service is registered as a singleton.
  
- **Exception Handling Granularity**: The AI proposed handling `ValidationException` in the global exception handler. However, since validation errors are handled by model state validation and return a 400 automatically via the `ApiController` attribute, this was removed to avoid duplication and rely on the built-in mechanism.

- **Route Design**: The AI initially considered using route parameters for filtering (`/api/expenses/category/{food}`). This was changed to query string parameters (`/api/expenses?category=food`) to better match RESTful filtering conventions and the explicit requirement in the task.

## Testing Performed

The following tests were written and executed to ensure correctness:

### Service Tests
- Add expense returns correct DTO
- Get all expenses returns all added expenses
- Get expenses by category returns only matching expenses
- Get total expenses returns correct sum
- Get total expenses by category returns correct sum for category
- Delete expense removes it from the collection
- Delete expense with non-existent ID throws `ExpenseNotFoundException`
- Get expense by ID returns null for non-existent ID

### Controller Tests
- Create expense returns 201 Created with correct location and body
- Get all expenses returns 200 OK with list of expenses
- Get expenses by category returns 200 OK with filtered list
- Get total expenses returns 200 OK with total amount
- Get total expenses by category returns 200 OK with category and total
- Delete expense returns 204 No Content
- Delete expense with non-existent ID returns 404 Not Found
- Create expense with validation errors returns 400 Bad Request with validation details

All tests pass successfully, confirming that the API meets the specified requirements.
